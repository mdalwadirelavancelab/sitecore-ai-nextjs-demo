# Shared site stylesheet setup

This folder contains the shared code for selecting a site's stylesheet.
Actual site designs belong in their own folders on the development branch.
The shared multisite branch includes `demo-site` as a developer reference.
Its SCSS demonstrates scoped header/footer styling. Its images and fonts folders
contain only placeholders. This is a code example, not a newly created CMS site.
It loads only when the fetched page's CMS site name is exactly `demo-site`.

## How it works

1. `src/Layout.tsx` reads `page.siteName` from the fetched Sitecore page.
2. `getSiteTheme` looks up that exact name in `siteThemes.ts`.
3. `SiteStyles` loads the selected stylesheet in the document head.
4. Layout adds `data-site-theme` to the wrapper, including in Page Builder.

A site without a registration uses the existing common and CMS styles.
This setup does not create CMS sites or replace the SDK's hostname routing.

## Add a design on the development branch

Copy the included `demo-site` folders and replace the name with the actual CMS
site name in the folders, SCSS wrapper, asset URLs and theme registration:

```text
src/Sites/demo-site/styles/
  main.scss
  sass/
    _header.scss
    _footer.scss
public/Sites/demo-site/
  images/
  fonts/
  styles/main.css             Generated by Sass; do not edit or commit
```

Keep `main.scss` as the stylesheet entry point. Put supporting SCSS files in
`sass/` and start their names with `_` so Sass does not generate separate CSS
files for them. The entry point loads them with `@use './sass/header'` and
`@use './sass/footer'`, then includes their mixins inside the site wrapper.
The generated URL remains `/Sites/demo-site/styles/main.css`.

Add its registration to the existing `siteThemes` object:

```ts
'demo-site': {
  name: 'demo-site',
  stylesheet: '/Sites/demo-site/styles/main.css',
},
```

Scope the site's SCSS to its wrapper:

```scss
[data-site-theme='demo-site'] {
  .site-header {
    background: #fff;
  }
}
```

React can retain stylesheets after client navigation. Scoping prevents one
site's retained CSS from styling another site's content. Avoid global `html`,
`body` and `:root` selectors in site styles. Portals outside the wrapper need
their own site scope. Give font families and keyframes site-specific names.

Use root-relative asset URLs such as `/Sites/demo-site/images/banner.png`.
Keep site images and fonts in Git; only compiled stylesheet folders are ignored.

## Why package.json changes

Browsers need CSS, so Sass builds a separate file for each site's SCSS entry.
Importing every site's SCSS into the root layout would load all designs together.
JSON does not allow comments, so the script explanation lives here.

- `styles:sites:build` compiles compressed CSS before the app starts or builds.
  Sass mirrors `src/Sites` under `public/Sites`. Underscore partials do not
  produce separate stylesheets. The command also succeeds with no site SCSS.
- `styles:sites:watch` compiles changed SCSS during development. Refresh the
  browser to see changes; this watcher does not provide Next.js CSS hot reload.
- `dev` builds styles first, then runs Sass and the existing app watchers.
- `build` builds styles before Sitecore generation and the Next.js build.

Sass is already installed; no new dependency or lockfile update is required.
Restart `npm run dev` after changing scripts. Deploy with `npm run build` and
include generated public assets. Calling `next build` alone skips site Sass.
Compilation does not remove old output from renamed or deleted source files.

## Existing framework styles

Bootstrap, Core UI and the existing global Tailwind setup remain shared.
This change separates custom site styles, not the framework bundles.

## Enable or disable one site's design

To enable a design, add its SCSS and register the exact CMS site name in
`siteThemes.ts`. Run `npm run styles:sites:build` or restart `npm run dev`.
Check that the page wrapper has the expected `data-site-theme` value and that
its `/Sites/<site>/styles/main.css` request succeeds.

To disable a design temporarily, remove only its entry from `siteThemes.ts`.
Keep its source and assets if it may be enabled again. The site's routing,
content, Core UI and existing global styles continue to work. A full browser
reload clears a stylesheet that React may have retained after navigation.

## Remove the demo or another site's folders

1. Remove that site's entry from `siteThemes.ts`.
2. Check references to its images, fonts and stylesheet, including CMS HTML.
3. Delete only `src/Sites/<site>` and `public/Sites/<site>` once their assets
   are no longer used. For this reference, replace `<site>` with `demo-site`.
4. Remove the old generated CSS too. Sass does not delete stale output.
5. Rebuild and check for missing asset requests. Do not delete another site's
   folders or the shared `SiteStyles.tsx` and `siteThemes.ts` files.

Deleting code folders does not delete a CMS site. Remove or disable a CMS site
separately only when it is no longer needed.

## Remove all custom site stylesheet support

Use this only when no site needs this mechanism:

1. In `src/Layout.tsx`, remove the SiteStyles/getSiteTheme imports, the
   siteTheme lookup, the SiteStyles element and the data-site-theme attribute.
   Keep the existing body attributes, placeholders and CMS SitecoreStyles.
2. In `package.json`, remove `styles:sites:build` and `styles:sites:watch`.
   Remove their task names from `build` and `dev`, keeping the other tasks.
3. After checking asset references, remove `src/Sites` and unused public site
   assets. If other site features have since been added there, keep those files.
4. Remove the generated-styles rule from `.gitignore` and this README link
   from the root README if this documentation is also deleted.
5. Keep Sass installed: Core UI still uses SCSS. Restart and test the app.

## Multisite routing is separate from site styles

`AppRouterMultisiteProxy` in `src/proxy.ts` resolves the site for incoming
requests. Theme registration does not enable or disable that SDK routing.
To serve several sites, configure their CMS site hosts and rendering host,
publish the required configuration/content and refresh SDK-generated site data
through the project's normal Sitecore build process. Do not manually maintain
`.sitecore/sites.json` or use the demo theme as a routing fallback.

For a single-site deployment, keep the existing SDK routing and configure the
intended site/host and default site. This is the simplest way to retain the
current `[site]/[locale]/[[...path]]` route structure and Page Builder support.

Do not simply delete `[site]`, remove AppRouterMultisiteProxy, or set
`multisite.enabled` to false. Fully disabling SDK multisite routing is a
separate route migration: update route folders, site parameter consumers,
Bootstrap, page fetching, dictionary lookup, static paths and editing routes
together. Test normal pages and Page Builder before releasing that migration.
No such migration is performed by the stylesheet setup in this branch.

## Branch workflow

Start `multisite` from `main` and commit shared setup changes there.
Merge those commits into `develop`, where site registrations, SCSS, images
and fonts live. Preserve existing site registrations when resolving conflicts.
Do not merge development site designs back into the shared branch.
Stop and restart the dev server when switching branches.
